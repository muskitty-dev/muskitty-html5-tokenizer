# LLM Authorship Disclosure

This document discloses the LLM authorship of `muskitty-html5-tokenizer`,
in accordance with This Week in Rust's submission policy.

## Summary

The HTML5 tokenizer logic in this crate was generated by an LLM-based
coding agent (GLM-5.2 via TRAE IDE), supervised by a human developer.
The crate was extracted from `muskitty-html5-parser` (commit c233c74
in the workspace root) as a standalone crate to allow reuse by syntax
highlighters, HTML sanitizers, and lint tools without dragging in DOM
or tree construction.

## Origin

This crate was originally developed inside `muskitty-html5-parser` as
the `src/tokenizer/` module. See
[muskitty-html5-parser/LLM_GENERATION.md](https://github.com/muskitty-dev/muskitty-html5-parser/blob/main/LLM_GENERATION.md)
for the full LLM authorship disclosure covering the tokenizer's
implementation history, test-feedback loop, and spec citation discipline.

## What the LLM Did

1. **Implemented the tokenizer** (§13.2.5) — all 85 states of the
   HTML5 tokenizer state machine, including:
   - Content model switching (RCDATA, RAWTEXT, ScriptData, PLAINTEXT)
   - Named character reference resolution (2231 entities, binary search)
   - Numeric character references (decimal + hex)
   - Windows-1252 replacement table
   - Processing instruction and CDATA section states
   - Reentrant design (tree construction can pause/resume tokenizer)

2. **Diagnosed and fixed its own bugs** — when the test harness
   reports a failure, the agent reads the failing input, the expected
   output, and the relevant spec section, then proposes a fix.

3. **Selected Rust idioms** — the agent chose `Vec<char>` for the
   input stream, `match` on `State` for dispatch, and `enum` for
   the state machine. These choices were not directed by the human.

## What the Human Did

1. **Authored the project constitution** — three hard rules that the
   agent must follow at all times:
   - WHATWG spec is ground truth (spec > WPT > Chromium when they conflict)
   - Safe Rust only (zero `unsafe`, zero C/C++ deps)
   - Spec-compliant, not test-compliant (never modify a test to pass it
     unless the spec proves the test is wrong, with chapter citation)

2. **Built the test-feedback loop** — a harness that runs
   `cargo test --test html5lib_tokenizer`, captures per-fixture
   pass/fail counts, and feeds failing test cases back to the agent
   with the expected token stream and the relevant WHATWG spec section.

3. **Reviewed every commit** — the human reads every diff before
   `git commit`.

## Test Results

- **Tokenizer**: 99.8% (7022/7036) on html5lib tokenizer suite
  - 14 failures are XML processing instructions, which the spec
    defines as parse errors; the tests expect them to be tokenized
    as comments, which is spec-intentional divergence
